# 包装库扩展判定规则

> 模式 A（包装库扩展）新增方案前的强制前置流程。判定新方案与已有方案是否重复，决定是否接受新增。
> 本规则最终决定权归用户：默认按矩阵处理，用户可随时推翻任何判定结果。

## 模式 A：实施边界

先读包装索引与本文件，确认不是重复方案；需要对照已有风格时才读参考分析或相应拆解文档。仅归档风格不新增通用组件，只更新风格索引与目标风格文档；包装索引通过链接发现风格，不复制配方、别名或单片验收状态。真正新增组件／API 或改变方案适用范围时，再更新包装索引并执行本文件的相应扩展判定。

通用组件在 `remotion-clone/src/components/`，跨风格共享常量在 `lib/theme.ts`；独立风格令牌放 `styles/`，不得通过修改共享主题给所有片换肤。参考场景按“语义任务 × 使用环境”归并；只有逐镜复刻或同步诊断任务才以镜头时序为主。片级明确要求不能被风格名静默取消。

包装组件 API 变化时按[验证规则](../workflows/verification.md)核对当前组件、实际调用与方案文档；归档项目不作为当前扩展的前置验证。

## 三维判定标准

判定一个新方案是否与已有方案重复，从三个维度依次检查：

### 维度 1 - 使用场景重合（最关键）

- **判据**：新方案的"使用场景"描述与已有方案是否指向同一类问题
- 例：新方案"段首大标题" vs 已有 `GlowTitle` -> 重合
- 例：新方案"圆角矩形信息卡" vs 已有 `HighlightTag` -> 部分重合，需进一步判定

### 维度 2 - 视觉配方重合

- **判据**：颜色 / 形状 / 尺寸 / 动效是否高度相似
- 例：新方案"黄色描边 + 外发光 + 脉冲" vs 已有 `HighlightBox` -> 完全重合
- 例：新方案"圆形头像 + 紫色渐变描边" vs 已有 `CircularAvatar` -> 完全重合

### 维度 3 - 参数空间重合

- **判据**：props 列表是否能互相替换
- 例：新方案的 props 与已有方案几乎一致，只换名字 -> 重复
- 例：新方案 props 是已有方案 props 的子集 -> 重复

## 判定矩阵与处理

| 重合维度数 | 判定 | 默认处理 |
| --- | --- | --- |
| 0 | 完全新增 | 直接加入 |
| 1 | 合理扩展 | 直接加入 |
| 2 | 边界情况 | **询问用户决定** |
| 3 | 完全重复 | 拒绝新增 |

## 用户的调整权

以上判定结果为默认行为，用户可随时推翻，包括但不限于：

- 把维度 2 的边界情况直接判定为接受或拒绝（不询问）
- 把维度 3 的"完全重复"判定为"接受但需重构"
- 把维度 0/1 的"直接加入"改回询问
- 要求对某个已有方案做"扩展"而非新增（即使判定为 0/1）

主会话在报告判定结果时，必须明确标注"默认建议"与"等待用户确认"两类，不得擅自执行维度 2 的新增。

## 操作流程

1. 读 [`README.md`](./README.md) 主索引，扫所有方案名 + 一句话场景
2. 找候选重合方案（同类下优先，跨类下次要）
3. 读候选方案完整文档的"使用场景"+"怎么使用"+"视觉配方"三节
4. 按三维判定，统计重合维度数
5. 按判定矩阵处理：
   - **0 或 1 维度重合**：直接加入，写方案文档 + 更新主索引
   - **2 维度重合**：向用户报告候选重合方案 + 三维对比 + 默认建议，由用户决定
   - **3 维度重合**：拒绝新增，向用户报告重复原因，建议扩展已有方案

## 判定为 2 维度重合时的询问格式

向用户报告时必须包含：

1. **新方案**：方案名 + 一句话使用场景
2. **候选重合方案**：方案名 + 一句话使用场景
3. **三维度对比表**：

   | 维度 | 新方案 | 候选方案 | 是否重合 |
   | --- | --- | --- | --- |
   | 使用场景 | ... | ... | ✅ / ❌ |
   | 视觉配方 | ... | ... | ✅ / ❌ |
   | 参数空间 | ... | ... | ✅ / ❌ |

4. **默认建议**：基于视觉配方差异判断"扩展已有"或"接受新增"
5. **询问用户决定**：接受新增 / 拒绝 / 改为扩展已有方案

## 当前包装库已有的边界案例

已有方案中存在几对"相似但已论证差异"的，可作为判定参照；分类计数以包装库主索引为准，不在本页另维护一份总数：

| 对比 | 差异点 | 论证依据 |
| --- | --- | --- |
| `HighlightTag` vs `HighlightBox` | 前者色块卡独立于 B-roll，后者 B-roll 内描边框 | 使用场景不重合 |
| `StepList` vs `StepFlowBar` | 前者垂直详细列表，后者底部水平总览 | 视觉配方不重合（互斥使用） |
| `GlowTitle` vs `HighlightTag` | 前者段首大标题无色块底，后者色块信息卡 | 视觉配方 + 参数空间均不重合 |
| `RoundedUIFrame` vs `HighlightBox` | 前者是 B-roll 容器（圆角 + 投影），后者是 B-roll 内区域高亮（描边 + 发光） | 使用场景 + 视觉配方均不重合 |

这些对在当初新增时如果按本规则判定，多数会落在维度 1（合理扩展），差异论证已在各自文档中固化。

## 重复时的替代方案：扩展已有方案

如果判定为重复（维度 2 询问后用户选择扩展 / 维度 3 拒绝后仍需实现需求），优先考虑：

- 给已有方案加新 prop（如 `HighlightTag` 加新 color 选项）
- 给已有方案加新 variant（如 `GlowTitle` 的 'glow' | 'plain' 模式）
- 在已有方案文档补一节"高级用法"覆盖新场景

扩展后必须：
- 更新方案文档的 props 列表 / variant 列表
- 更新 `README.md` 主索引（如使用场景描述有变）
- 沉淀到 `04-design-log.md`（如扩展过程中有新发现）

## 新增方案后的清单

判定为接受新增后，必须完成以下全部步骤才算扩展完成：

1. 实现源码到 `remotion-clone/src/components/` 等对应目录
2. 写方案文档到 `docs/packaging-library/{components,layouts,animations,masks,transitions}/` 对应子目录
3. 更新 `docs/packaging-library/README.md` 主索引（方案名、使用场景、链接及分类计数）；新增、删除、改用途或计数时，索引与方案文档必须双向同步，不能只改一处
4. 如涉及新坑，沉淀到 `docs/packaging-library/pitfalls.md`
5. 如涉及新音效规则，更新 `docs/packaging-library/sfx-rules.md`
6. 如涉及新常量，跨风格共享常量更新 `remotion-clone/src/lib/theme.ts`，独立风格令牌放 `remotion-clone/src/styles/`；不将某风格外观写成所有片的共享默认值

漏掉任何一步都视为扩展未完成，主索引与实际方案会脱节。
